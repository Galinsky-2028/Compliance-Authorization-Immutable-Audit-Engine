# Free-plan demonstration deployment

The root `render.yaml` describes a zero-cost demonstration of the engine on
Render free web services with a Neon free-plan PostgreSQL project. It exists so
thin downstream applications (Algorithmic Accountability, Federal Encryption
Compliance) can exercise the real API in demonstration mode. It is **not** the
production topology in [render-production-deployment.md](render-production-deployment.md)
and does not establish production acceptance, SLOs, recovery objectives or
certification.

## Current demonstration instance

- `caiae-api`: `https://caiae-api.onrender.com` (Render free web service, Ohio).
- `caiae-admin`: `https://caiae-admin.onrender.com` (Render free web service, Ohio).
- Database: Neon project **CAIAE** (AWS us-east-2) in the campaign organization.
- Demonstration tenants: `algorithmic-accountability-demo` and
  `federal-encryption-compliance-demo`. Their client values are in the Render
  environment groups `caiae-client-algorithmic-accountability-demo` and
  `caiae-client-federal-encryption-compliance-demo`.

## Topology

| Service | Render type | Start | Purpose |
| --- | --- | --- | --- |
| `caiae-api` | Free web service | `node scripts/start-free-plan.mjs` | Migrations, optional demonstration tenants, Fastify API and the sweep worker in one container. |
| `caiae-admin` | Free web service | `npm run start -w @caiae/web` | Reference admin UI; proxies `/engine-api/*` to `caiae-api` through `CAIAE_API_BASE_URL`. |

Render has no free background-worker plan, so `scripts/start-free-plan.mjs`
supervises two child processes in the API service: `apps/api/dist/server.js`
and `apps/worker/dist/worker.js`. Before starting them it applies migrations
once and then runs both children with `CAIAE_RUN_MIGRATIONS=false`. A platform
SIGTERM is forwarded to both children. If either child exits on its own, the
other is stopped and the container exits non-zero, so Render restarts the pair
together rather than serving an API without sweeps.

Both children read `RENDER_GIT_COMMIT`, so the worker release matches the API
release and `GET /ready?includeWorker=true` reports full-system readiness.
`GET /ready` (the Render health check) remains API and database only.

## Free-plan limits

- Free web services sleep after a period without inbound traffic. While the
  API sleeps, **sweeps do not run**: authorization and exception expiry,
  deadline clocks, evaluations, certification renewal checks and webhook
  delivery resume only when a request wakes the service. Sweeps are
  time-based and catch up on the next run, but nothing is processed while the
  service is asleep. Use the paid topology with an always-on worker for any
  real obligation.
- One instance only. The worker is not leader-elected; never scale this
  service beyond one instance.
- The first request after sleep is slow (cold start plus Neon compute resume).
- The filesystem is ephemeral; the engine stores evidence references, not
  files.
- Neon free-plan compute, storage and restore-window limits apply. Arrange
  logical backups before storing anything other than demonstration data.

## Build

`NODE_ENV=production` is set on the services and is visible during the Render
build, which would make `npm ci` skip devDependencies (TypeScript and Node
type definitions). The build command therefore uses
`npm ci --include=dev && npm run build`.

## Database

Create a dedicated Neon project in the campaign organization (AWS us-east-2,
next to Render's Ohio region). Set `DATABASE_URL` on `caiae-api` to the
**direct** (non-pooler) connection string with `sslmode=verify-full`. The
service is small enough to use the direct connection for both migrations and
traffic. Never commit the connection string.

## Secrets and configuration

| Variable | Service | Source |
| --- | --- | --- |
| `DATABASE_URL` | `caiae-api` | Neon direct connection string, set on Render only. |
| `CAIAE_WEBHOOK_MASTER_SECRET` | `caiae-api` | Generated by Render. |
| `CAIAE_CORS_ORIGINS` | `caiae-api` | `none`; the admin UI uses a server-side rewrite. |
| `CAIAE_DEMO_TENANTS`, `CAIAE_DEMO_TENANTS_CONFIRM` | `caiae-api` | Optional demonstration tenants (below). |
| `CAIAE_API_BASE_URL` | `caiae-admin` | The API's Render URL (required at build time for the rewrite). |

`CAIAE_BOOTSTRAP_SECRET` is deliberately **not** set. The HTTP bootstrap
endpoint is only needed for the first production operator and should not stay
enabled on a public demonstration API. Production tenants follow
[production-tenant-bootstrap.md](production-tenant-bootstrap.md).

## Demonstration tenants for downstream applications

`scripts/provision-demo-tenants.mjs` runs at startup when `CAIAE_DEMO_TENANTS`
is set and `CAIAE_DEMO_TENANTS_CONFIRM=PROVISION_DEMO_TENANTS`. Each entry
creates (idempotently) one clearly labeled fictional organization, one active
operator principal with the organization administrator role, and one operator
credential registered **by digest**:

```json
[{
  "slug": "example-app-demo",
  "organizationName": "Example App demonstration (fictional)",
  "operatorName": "Example App demonstration client",
  "tokenPrefix": "<10 hex characters>",
  "tokenSha256": "<SHA-256 hex of the full token>"
}]
```

Slugs must end in `-demo` and names must say they are a fictional
demonstration. The plaintext operator token is generated outside Render's API
service in the standard `caiau_<prefix>_<secret>` form; only its prefix and
digest are configured on `caiae-api`, so the API host never holds or logs the
token. Startup logs print only `slug`, `organizationId`, `principalId` and
whether a credential was created.

Downstream applications receive their values through a Render environment
group (one per application) holding:

- `CAIAE_API_BASE_URL`: the `caiae-api` URL;
- `CAIAE_ORGANIZATION_ID`: the logged `organizationId` for that tenant;
- `CAIAE_OPERATOR_TOKEN`: the plaintext token whose digest is configured.

Link the group to the downstream service. To rotate a token, generate a new
one, replace the digest (the credential name `downstream-demo-operator` is
fixed, so first revoke the old credential through the API with an
administrator credential) and update the environment group. Provisioning
refuses to attach a different digest to an existing credential name.

## Deploy and verify

1. Create the Neon project and the two free web services from `render.yaml`
   (or the equivalent API calls), setting `DATABASE_URL` as a secret.
2. Watch the `caiae-api` deploy reach `live`. The logs must show
   `caiae_supervisor.migrations_applied`, any `caiae_demo_tenant.ready` lines,
   API listening, and the worker's sweep events.
3. Confirm `GET /ready` and `GET /ready?includeWorker=true` return 200, then
   `GET /v1/security/me` with a demonstration token returns its organization.
4. Deploy `caiae-admin` after the API URL is known and confirm `/` loads.

The manual Production Acceptance workflow and Engine Room monitor target the
production topology; do not treat this demonstration as accepted production.
